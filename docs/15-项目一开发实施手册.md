## 一、这份文档怎么使用

这是一份可以直接照着执行的开发施工文档。开发时按以下顺序使用：

1. 先读“项目边界”和“核心业务规则”，确认这一版做什么、不做什么。
2. 按“技术栈与版本策略”创建前后端项目。
3. 按“推荐开发顺序”逐个打通业务闭环，不要同时铺开所有模块。
4. 开发预约功能前，重新精读“并发预约实现方案”。
5. 每完成一个阶段，按对应验收项自测并提交 Git。
6. 数据库完整 DDL 以 `11-项目一数据库设计.md` 为准，本手册重点说明代码如何实现。

项目的最高优先级不是页面数量，而是以下四项：

- 能从登录一路演示到预约完成；
- 并发预约不会产生重复占用；
- 有真实压测记录；
- 2026 年 11 月底前部署上线。

## 二、项目目标与范围

### 2.1 业务目标

为校园研讨室、琴房、实验室、球场和公共设备提供统一预约入口，解决微信群接龙或纸质登记带来的以下问题：

- 同一资源的同一时段被多人重复预约；
- 用户占用资源但不到场，无法追踪违约；
- 部分重要资源需要审批，但审批过程没有记录；
- 管理员无法快速查看资源使用情况；
- 用户不知道某个资源未来哪些时段仍然可用。

### 2.2 目标用户

系统第一版只设计两种角色，不做通用 RBAC：

| 角色 | 权限 |
| --- | --- |
| `STUDENT` | 注册登录、浏览资源、查看可用时段、创建预约、取消预约、签到、查看自己的记录 |
| `ADMIN` | 管理资源和开放规则、审批预约、查看异常记录、执行必要的后台管理操作 |

### 2.3 第一版必须完成的功能（P0）

1. 用户注册、登录和 JWT 鉴权；
2. 学生与管理员角色控制；
3. 资源分类、资源、开放时间和闭馆日管理；
4. 查询某个资源未来 7 天的可用时间片；
5. 创建预约、取消预约、查看我的预约；
6. 需要审批的资源进入待审批状态；
7. 管理员审批通过或驳回；
8. 用户签到；
9. 超时未签到自动标记为 `NO_SHOW`；
10. 30 分钟时间片离散化；
11. 数据库唯一索引防止并发重复预约；
12. Redisson 分布式锁作为冲突优化层；
13. Vue 管理和操作页面；
14. Docker + Nginx 部署，公网可访问；
15. JMeter 并发测试报告。

### 2.4 进度正常时再完成的功能（P1）

- 违约扣分；
- 自动黑名单；
- Redis 缓存可用时段；
- AOP 操作日志；
- 预约结束后自动转为 `COMPLETED`；
- 简单资源使用率统计；
- 站内通知。

### 2.5 进度落后时直接砍掉的功能（P2）

- 通用角色与权限配置；
- 复杂统计大屏；
- 短信、邮件、微信通知；
- 地图、二维码门禁和学校统一身份认证；
- 多校区、多租户；
- 复杂图片管理；
- 微服务、Kafka、Elasticsearch、Kubernetes。

## 三、技术栈与版本策略

### 3.1 后端技术栈

| 技术 | 用途 | 选择理由 |
| --- | --- | --- |
| JDK 17 | Java 运行环境 | LTS 版本，满足 Spring Boot 3 要求，生态稳定 |
| Spring Boot 3.5.x | 应用框架 | 与当前学习资料和企业存量生态更匹配；不要使用 4.x |
| Spring MVC | REST API | 处理 HTTP 请求，适合当前同步业务模型 |
| Spring Security 6 | 登录鉴权和角色控制 | 比手写拦截器更规范，版本由 Spring Boot 管理 |
| Spring Security OAuth2 JOSE | JWT 编码与解码 | 使用 Spring Security 自带能力，避免自己实现 JWT 校验细节 |
| MyBatis-Plus | 数据访问 | 国内 Java 项目常见，简单 CRUD 快，复杂 SQL 可自己控制 |
| MySQL 8.0 | 业务数据库 | 事务、唯一索引和查询能力满足预约系统需求 |
| Spring Data Redis | 缓存 | 用于可用时段缓存，不把 Redis 当最终数据源 |
| Redisson | 分布式锁 | 提供可重入锁和看门狗续期，避免手写 `SETNX` 锁 |
| Spring Task | 定时任务 | 当前单体项目足够使用，暂不引入 XXL-Job |
| Bean Validation | 参数校验 | 通过 `@Valid`、`@NotBlank` 等统一校验请求参数 |
| BCrypt | 密码哈希 | 带盐慢哈希，禁止明文、MD5 或 SHA-1 存密码 |
| springdoc-openapi | 接口文档 | 自动生成 OpenAPI 文档，便于联调和演示 |
| Logback + SLF4J | 日志 | Spring Boot 默认方案，支持分级、文件滚动和问题排查 |
| JUnit 5 + MockMvc | 自动化测试 | Spring Boot 默认测试体系，覆盖核心规则和接口 |
| JMeter | 并发压测 | 用于复现和验证重复预约问题 |
| Maven | 构建和依赖管理 | Java 主流构建工具 |

版本执行规则：

1. Spring Boot 使用创建项目时可用的最新稳定 `3.5.x` 补丁版本。
2. Spring Framework、Spring Security、Jackson、JUnit 等由 Spring Boot BOM 管理，不手动覆盖版本。
3. MyBatis-Plus 使用 Boot 3 专用 starter，并通过官方 BOM 或统一属性锁定一个经过验证的版本。
4. Redisson、springdoc-openapi 等第三方依赖，在创建项目时查官方兼容说明后锁定版本，不写动态版本。
5. 项目能稳定运行后，不为了“追新”随意升级依赖。

## 四、系统架构

### 4.1 逻辑架构

```text
浏览器
  |
  | HTTPS
  v
Nginx
  |-- /                 -> Vue 静态文件
  `-- /api/*            -> Spring Boot:8080
                              |
                              |-- Controller：请求接收、参数校验、权限入口
                              |-- Application/Service：业务编排、事务、状态流转
                              |-- Domain：状态枚举、规则和时间片逻辑
                              `-- Mapper：MyBatis-Plus 和自定义 SQL
                                      |
                                      |-- MySQL：业务真相、事务、唯一约束
                                      `-- Redis：缓存、分布式锁
```

### 4.2 部署架构

第一版保持单体部署：

```text
一台云服务器
  |
  |-- Nginx 容器：80/443
  |-- booking-web 静态文件
  |-- booking-api 容器：仅 Docker 内网开放 8080
  |-- MySQL 容器：仅 Docker 内网开放 3306
  `-- Redis 容器：仅 Docker 内网开放 6379
```

生产环境只公开 80 和 443 端口。MySQL 和 Redis 不应直接暴露到公网。

### 4.3 为什么使用单体架构

- 业务规模小，模块之间事务关系强；
- 预约创建和时间片写入需要本地数据库事务；
- 当前只有一个开发者，微服务会增加部署、日志和调试成本；
- 单体不等于代码混乱，仍然要按业务模块和分层组织代码。

分层职责：

| 层 | 可以做 | 不应该做 |
| --- | --- | --- |
| Controller | 接请求、`@Valid`、权限注解、调用服务、返回 VO | 写 SQL、拼业务规则、开启复杂事务 |
| Service | 业务规则、事务、状态流转、多个 Mapper 编排 | 直接处理 HTTP 对象、返回 Entity |
| Mapper | 查询和写入数据库 | 决定业务状态、调用远程接口 |
| Entity | 映射数据库字段 | 直接作为请求或响应对象 |
| DTO | 接收请求参数 | 携带密码等不需要的数据库字段 |
| VO | 返回前端所需内容 | 暴露密码、删除标记等内部字段 |

## 六、统一工程规范

### 6.1 统一响应

建议响应结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

分页响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "records": [],
    "pageNumber": 1,
    "pageSize": 10,
    "total": 0
  }
}
```

错误码按模块分段，避免到处使用魔法数字：

| 范围 | 模块 | 示例 |
| --- | --- | --- |
| `40000-40099` | 通用参数错误 | 参数为空、格式错误 |
| `40100-40199` | 登录鉴权 | Token 无效、登录过期 |
| `40300-40399` | 权限 | 非管理员访问后台接口 |
| `40400-40499` | 数据不存在 | 资源或预约不存在 |
| `41000-41099` | 用户业务 | 用户禁用、信用不足 |
| `42000-42099` | 资源业务 | 资源停用、闭馆 |
| `43000-43099` | 预约业务 | 时段冲突、非法状态流转 |

HTTP 状态码仍然应正确使用：

- 参数错误：400；
- 未登录：401；
- 无权限：403；
- 数据不存在：404；
- 资源冲突：409；
- 未知服务端异常：500。

### 6.2 参数校验

Controller 只接收 DTO，并使用 Bean Validation：

- 用户名：非空、长度限制；
- 密码：非空、最低长度；
- 手机号：格式校验；
- 预约开始和结束时间：非空；
- 参与人数：大于 0；
- 预约用途：限制长度；
- 审批驳回时：意见不能为空。

字段格式校验由 DTO 完成，跨字段和数据库相关规则由 Service 完成。例如“结束时间必须晚于开始时间”属于跨字段业务校验，不要只依赖前端。

### 6.3 时间处理

项目只服务一个中国校区，第一版统一使用：

- Java：`LocalDate`、`LocalTime`、`LocalDateTime`；
- MySQL：`DATE`、`TIME`、`DATETIME`；
- 时区：`Asia/Shanghai`；
- JSON 时间格式：`yyyy-MM-dd HH:mm:ss`；
- 数据库连接显式配置服务器时区。

禁止在业务代码中混用 `Date`、字符串和 `LocalDateTime`。

如果未来支持多时区，再改为 UTC 存储和带时区的时间类型。当前不要提前复杂化。

### 6.4 Long 精度处理

Java 的 `Long` 最大值超过 JavaScript 安全整数范围。后端应统一把 Long 类型 ID 序列化为字符串，防止前端收到 ID 后发生精度丢失。

### 6.5 日志规范

日志至少包括：

- 请求的 traceId；
- 当前用户 ID；
- 核心业务 ID，如 bookingNo；
- 操作结果；
- 异常堆栈；
- 关键接口耗时。

禁止记录：

- 明文密码；
- 完整 JWT；
- 数据库密码和 Redis 密码；
- 手机号等敏感信息的完整值；
- 不受限制的大段请求体。

不要使用 `System.out.println`。

### 6.6 配置与密钥

建议配置分为：

```text
application.yml
application-local.yml
application-test.yml
application-prod.yml
```

生产密码、JWT 私钥或密钥只能通过环境变量传入，不提交到 Git：

```yaml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

booking:
  security:
    jwt-secret: ${JWT_SECRET}
```

仓库中只提交 `.env.example`，不能提交真实 `.env`。

## 七、数据库实现要求

完整 SQL 见 `11-项目一数据库设计.md`。代码开发前必须理解以下关键表：

| 表 | 作用 | 实现重点 |
| --- | --- | --- |
| `user` | 用户、角色和信用分 | 密码必须 BCrypt；不要返回密码字段 |
| `resource` | 资源及预约规则 | 最大提前天数、最长时长做成配置字段 |
| `resource_time_rule` | 每周开放时间 | 一天可以配置多个开放区间 |
| `resource_closure` | 特殊闭馆日 | `resource_id=0` 表示全局闭馆 |
| `booking` | 预约主记录 | 保存完整历史和状态机 |
| `booking_slot` | 当前有效时间片占用 | 物理删除；唯一索引保证并发正确性 |
| `approval_record` | 审批留痕 | 只新增，不修改历史记录 |
| `violation_record` | 违约和幂等记录 | 唯一索引防重复扣分 |

数据库规则：

1. 使用 InnoDB 和 utf8mb4。
2. 不加物理外键，但 Service 必须检查关联数据存在性。
3. 预约历史采用逻辑删除或不提供删除入口。
4. `booking_slot` 必须物理删除，不能使用逻辑删除。
5. 所有更新语句尽量带明确状态条件，避免并发状态覆盖。
6. 只为真实查询建立索引，并用 `EXPLAIN` 验证。
7. SQL 迁移脚本进入 `sql/`，按序号管理，禁止上线后手改表却不留脚本。

推荐脚本组织：

```text
sql/
├── V001__create_database.sql
├── V002__create_user_and_resource_tables.sql
├── V003__create_booking_tables.sql
├── V004__create_support_tables.sql
└── V005__insert_demo_data.sql
```

第一版可以手动执行这些脚本；有余力再接入 Flyway 自动迁移。

## 八、核心业务规则

### 8.1 创建预约前的校验顺序

建议严格按以下顺序执行，先做便宜校验，再做数据库和锁操作：

1. 请求参数非空和格式校验；
2. 开始时间早于结束时间；
3. 开始和结束时间必须在同一天；
4. 时间必须对齐 30 分钟边界，秒和纳秒必须为 0；
5. 开始时间必须晚于当前时间；
6. 预约时长满足资源的最短和最长限制；
7. 预约日期不超过资源允许的最大提前天数；
8. 资源存在、未删除且状态为可用；
9. 参与人数不超过资源容量；
10. 当天不是全局或资源闭馆日；
11. 预约区间完全落在当天某个开放时间规则内；
12. 用户状态正常；
13. 用户当前不在黑名单；
14. 用户持有的未结束预约数量没有超过上限；
15. 获取资源和日期维度的分布式锁；
16. 在事务内创建预约主表和时间片记录；
17. 提交成功后删除对应日期的可用时段缓存。

前端校验只用于改善体验，后端必须完整重复全部业务校验。

### 8.2 时间片规则

系统固定使用 30 分钟粒度：

```text
[14:00, 16:00)
=> 14:00、14:30、15:00、15:30
```

使用左闭右开区间 `[startTime, endTime)`。这样 14:00-15:00 与 15:00-16:00 不冲突。

时间片拆分伪代码：

```java
List<LocalDateTime> splitIntoSlotTimes(
        LocalDateTime startTime,
        LocalDateTime endTime) {
    List<LocalDateTime> slotTimes = new ArrayList<>();
    LocalDateTime currentSlotTime = startTime;

    while (currentSlotTime.isBefore(endTime)) {
        slotTimes.add(currentSlotTime);
        currentSlotTime = currentSlotTime.plusMinutes(30);
    }

    return slotTimes;
}
```

该方法必须有单元测试，至少覆盖：

- 14:00-14:30 产生 1 个时间片；
- 14:00-16:00 产生 4 个时间片；
- 结束时间不应作为时间片插入；
- 不对齐 30 分钟的时间应在进入拆分前被拒绝。

### 8.3 状态机

预约状态：

```text
PENDING_APPROVAL
  |-- APPROVE --> CONFIRMED
  |-- REJECT  --> REJECTED
  `-- CANCEL  --> CANCELLED

CONFIRMED
  |-- CHECK_IN --> CHECKED_IN
  |-- CANCEL   --> CANCELLED
  `-- TIMEOUT  --> NO_SHOW

CHECKED_IN
  `-- END_TIME_PASSED --> COMPLETED
```

状态规则：

- 不需要审批的资源创建后直接为 `CONFIRMED`；
- 需要审批的资源创建后为 `PENDING_APPROVAL`；
- `PENDING_APPROVAL` 从创建时就占用时间片，避免审批期间被其他人抢走；
- `CANCELLED`、`REJECTED`、`NO_SHOW` 必须在同一事务中删除时间片；
- `COMPLETED` 保留历史时间片没有业务价值，可在完成时删除，历史区间仍保留在 `booking`；
- 非法状态流转统一抛出业务异常，不能只依赖前端隐藏按钮；
- 状态判断集中在领域方法或状态规则类中，不要散落在多个 Controller。

建议定义显式方法：

```text
approveBooking()
rejectBooking()
cancelBooking()
checkInBooking()
markBookingAsNoShow()
completeBooking()
```

不要提供一个可以任意传入目标状态的 `updateStatus(status)` 公共接口，否则很容易产生非法流转。

### 8.4 取消规则

第一版建议采用简单规则：

- 开始时间前允许取消；
- 距开始时间不少于 2 小时取消，不记违约；
- 距开始时间不足 2 小时取消，状态仍为 `CANCELLED`，但新增 `LATE_CANCEL` 违约记录；
- 开始时间到达后不允许用户主动取消，由签到和未到场任务处理；
- 取消操作必须同时释放 `booking_slot`；
- 重复取消返回“当前状态不可取消”，不能重复扣分。

阈值先放在配置文件中，不必立刻加系统配置表：

```yaml
booking:
  rules:
    slot-minutes: 30
    late-cancel-hours: 2
    check-in-timeout-minutes: 15
    max-active-bookings: 3
```

### 8.5 签到规则

- 只有 `CONFIRMED` 可以签到；
- 最早可在开始前 15 分钟签到；
- 最晚可在开始后 15 分钟签到；
- 成功后状态改为 `CHECKED_IN`，记录 `checkin_time`；
- 第一版使用页面按钮签到，不接二维码和硬件门禁；
- 必须验证当前用户是预约发起人，管理员代签到如需支持应使用单独接口。

## 九、并发预约实现方案

这是项目一最重要的技术部分，开发、测试和文档都要围绕它保留证据。

### 9.1 第一阶段：故意保留有问题的版本

先实现下面的检查后插入逻辑，并用 JMeter 证明它有竞态条件：

```text
查询是否存在重叠预约
  |
  | 没有
  v
插入预约
```

两个请求可能同时查询到“没有冲突”，然后同时插入成功。必须保留：

- 复现步骤；
- JMeter 线程配置；
- 数据库重复预约截图；
- 原因分析。

这一步完成后立即修复，不能把有问题的版本长期部署在线上。

### 9.2 第二阶段：数据库唯一索引保证正确性

核心约束：

```sql
UNIQUE KEY uk_resource_slot (resource_id, slot_time)
```

预约创建事务：

```java
@Transactional(rollbackFor = Exception.class)
public BookingView createBooking(CreateBookingCommand command) {
    validateBookingRules(command);

    BookingEntity booking = buildBooking(command);
    bookingMapper.insert(booking);

    List<BookingSlotEntity> bookingSlots = buildBookingSlots(booking);
    try {
        bookingSlotMapper.insertBatch(bookingSlots);
    } catch (DuplicateKeyException exception) {
        throw new BookingSlotConflictException("该时段已被占用，请刷新后重试");
    }

    return buildBookingView(booking);
}
```

注意事项：

1. 预约主表插入和所有时间片插入必须在同一个事务里。
2. 批量插入建议用 MyBatis XML 的 `foreach` 编写一条批量 SQL。
3. 只要任何一个时间片冲突，整个事务都要回滚。
4. 业务异常应继承 `RuntimeException`，或明确配置事务回滚。
5. 不要吞掉 `DuplicateKeyException` 后返回成功。
6. 唯一索引是最终正确性防线，不能删除。

### 9.3 第三阶段：Redisson 分布式锁减少冲突

推荐锁 Key：

```text
booking:lock:{resourceId}:{bookingDate}
```

它比只使用 `resourceId` 粒度更细：同一资源不同日期的预约互不阻塞。由于第一版禁止跨日预约，所以这个粒度可以保证有重叠可能的请求进入同一把锁。

伪代码：

```java
String lockKey = buildBookingLockKey(resourceId, bookingDate);
RLock bookingLock = redissonClient.getLock(lockKey);
boolean acquired = bookingLock.tryLock(3, TimeUnit.SECONDS);

if (!acquired) {
    throw new BookingBusyException("当前预约请求较多，请稍后重试");
}

try {
    return transactionalBookingCreator.createBooking(command);
} finally {
    if (bookingLock.isHeldByCurrentThread()) {
        bookingLock.unlock();
    }
}
```

实现细节：

- 只传 `waitTime`，不要显式传 `leaseTime`，让 Redisson 看门狗负责续期；
- `unlock()` 前检查当前线程是否仍持有锁；
- 锁外完成参数格式、用户和资源等基础校验，缩短持锁时间；
- 最终的冲突敏感校验和数据库写入要放在锁内；
- Redis 不可用时，第一版可以返回“系统繁忙”，也可以降级到仅依赖数据库唯一索引；
- 无论是否降级，都不能移除数据库唯一约束。

### 9.4 事务代理注意事项

如果同一个 Service 中的非事务方法通过 `this.createBooking()` 调用带 `@Transactional` 的方法，事务可能因自调用绕过代理而失效。

建议将数据库事务部分拆到独立 Bean：

```text
BookingApplicationService
  |-- 参数校验
  |-- 获取 Redisson 锁
  `-- 调用 BookingTransactionalService.createBooking()

BookingTransactionalService
  `-- @Transactional 写 booking 和 booking_slot
```

这样事务边界清晰，也便于测试。

### 9.5 并发测试验收

至少执行三轮测试：

| 版本 | 并发请求 | 预期 |
| --- | ---: | --- |
| 错误基线版本 | 50-100 个请求抢同一时段 | 可能产生多个成功预约，用于复现问题 |
| 只有唯一索引 | 50-100 个请求抢同一时段 | 只能 1 个成功，其余返回 409 |
| 唯一索引 + Redisson | 50-100 个请求抢同一时段 | 只能 1 个成功，减少数据库唯一键冲突异常 |

同时再测一组不同资源或不同日期的请求，确认锁粒度没有造成不必要的全局串行。

压测报告至少记录：

- 硬件和软件环境；
- 线程数、启动时间和请求参数；
- 成功数、业务冲突数、异常数；
- 平均、P95、P99 响应时间；
- 数据库最终记录数；
- 三个版本的实现差异和结论。

不要把业务上的 409 冲突算成系统错误。系统错误应该是 500、连接失败或数据不一致。

## 十、定时任务与幂等性

### 10.1 未签到任务

每分钟扫描满足以下条件的预约：

```text
status = CONFIRMED
AND start_time <= 当前时间 - 15 分钟
```

每条预约独立事务处理：

1. 使用带状态条件的更新，只有 `CONFIRMED` 才能改为 `NO_SHOW`；
2. 插入 `violation_record`；
3. 扣减用户信用分；
4. 删除该预约全部 `booking_slot`；
5. 必要时生成通知。

幂等保障：

- `booking` 的状态条件避免已处理记录再次流转；
- `violation_record` 的 `(booking_id, violation_type)` 唯一索引避免重复违约；
- 状态更新、违约记录、扣分和释放时间片必须在同一事务；
- 一个预约处理失败不能回滚整批任务，建议按预约逐条调用独立事务方法。

### 10.2 自动完成任务

可每分钟扫描：

```text
status = CHECKED_IN
AND end_time <= 当前时间
```

把预约改为 `COMPLETED` 并删除时间片。完成任务属于 P1，如果进度落后，可以先由演示数据或管理员操作完成，但最终状态机文档必须说明这一点。

### 10.3 多实例问题

项目部署一个实例时，Spring Task 足够。若未来部署多个实例，每个实例都会执行定时任务。

可选演进方案：

- 使用 Redisson 为任务加分布式锁；
- 使用 ShedLock；
- 改用 XXL-Job 等分布式调度框架。

当前不要为了一个实例提前引入复杂调度平台，但要在项目文档中说明多实例限制。

## 十一、缓存设计

缓存是 P1，不要在预约正确性完成前接入。

### 11.1 缓存对象

缓存“某资源某天的可用时间片计算结果”：

```text
resource:available-slots:{resourceId}:{date}
```

建议过期时间为 5-15 分钟，并加入少量随机抖动，避免大量 Key 同时过期。

### 11.2 Cache Aside 流程

查询：

```text
查 Redis
  |-- 命中：返回
  `-- 未命中：查 MySQL并计算 -> 写 Redis -> 返回
```

写入：

```text
先提交 MySQL 事务
  `-- 事务成功后删除对应资源和日期的缓存
```

必须在事务提交成功后删除缓存，避免数据库回滚但缓存已被错误删除或重建。可以使用事务同步回调或事务提交后的应用事件。

以下操作都要失效缓存：

- 创建预约；
- 取消预约；
- 审批驳回；
- 未签到释放时段；
- 管理员修改开放规则；
- 管理员新增闭馆日；
- 资源状态发生变化。

### 11.3 缓存问题处理边界

- 不存在的资源可以短暂缓存空值，减少缓存穿透；
- 热门 Key 失效时可以使用互斥锁重建，属于后期优化；
- 第一版不引入布隆过滤器；
- Redis 缓存绝不能决定预约最终是否成功，预约创建仍以 MySQL 唯一索引为准。

## 十二、登录鉴权与安全细节

### 12.1 登录流程

```text
用户名和密码
  -> 查询用户
  -> BCrypt 校验
  -> 检查用户状态
  -> 生成短期 JWT
  -> 前端后续通过 Authorization: Bearer <token> 请求
```

JWT 最低包含：

- `sub`：用户 ID；
- `username`：用户名；
- `role`：角色；
- `iat`：签发时间；
- `exp`：过期时间。

第一版只做访问 Token，不做刷新 Token。过期后重新登录，减少实现复杂度。

### 12.2 Spring Security 路由策略

公开接口：

- 登录、注册；
- OpenAPI 文档是否公开由环境决定；
- 健康检查可以公开最小信息。

学生和管理员均可访问：

- 资源查询；
- 可用时段查询；
- 自己的预约、取消和签到。

仅管理员：

- 资源增删改；
- 开放时间和闭馆日配置；
- 审批列表、通过、驳回；
- 用户和统计管理。

Service 层仍然要校验数据归属。例如学生访问 `GET /bookings/{id}` 时，必须确认预约属于当前用户，不能只因为“已登录”就返回任意预约。

### 12.3 前端 Token 存储

第一版可以将短期 Token 保存到 `sessionStorage`，并通过 Axios 请求拦截器加入请求头。必须知道它仍然存在 XSS 风险。

生产级系统更常见的选择包括 HttpOnly Cookie、BFF 或更完整的 OAuth2/OIDC 方案。当前项目不展开，但 README 中可以说明取舍。

### 12.4 其他安全要求

- 注册接口限制用户名和密码长度，避免超大请求；
- 登录失败统一提示“账号或密码错误”，避免枚举账号；
- 生产环境配置登录限流属于 P1；
- 管理员接口以后端角色校验为准，不能只靠前端隐藏菜单；
- 操作日志中的密码和 Token 必须脱敏；
- 文件上传如果保留资源图片功能，必须校验大小、扩展名和 MIME 类型；
- Nginx 配置请求体大小上限；
- 生产数据库使用专用低权限账号，不直接使用 root。

## 十五、可用时段计算

查询某资源某一天的可用时间片时：

1. 查询资源，确认可用；
2. 检查查询日期不超过允许范围；
3. 检查全局闭馆和资源闭馆；
4. 根据星期几查询 `resource_time_rule`；
5. 将开放区间拆成 30 分钟时间片；
6. 查询当天 `booking_slot` 中已占用的时间片；
7. 过滤已经过去的时间片；
8. 返回每个时间片的可用状态。

推荐响应：

```json
{
  "resourceId": "1",
  "date": "2026-10-15",
  "slotMinutes": 30,
  "slots": [
    { "startTime": "08:00", "endTime": "08:30", "available": true },
    { "startTime": "08:30", "endTime": "09:00", "available": false }
  ]
}
```

这个查询结果只是界面展示依据，不能替代创建预约时的数据库唯一约束。用户看到可用到点击提交之间，其他人仍然可能先完成预约。

## 十六、测试方案

### 16.1 必须写的单元测试

| 测试对象 | 核心用例 |
| --- | --- |
| 时间片拆分 | 数量、边界、左闭右开 |
| 时间对齐校验 | 00/30 合法，15/45 非法 |
| 预约时长规则 | 最短、最长、越界 |
| 开放时间规则 | 完全包含合法，跨越闭馆区间非法 |
| 状态机 | 合法流转成功，非法流转失败 |
| 取消违约判断 | 2 小时边界前后 |
| 签到窗口 | 开始前、允许区间、超时 |

### 16.2 必须写的集成测试

- 注册后密码不是明文；
- 登录成功能获得 Token，错误密码返回 401；
- 学生不能访问管理员接口；
- 创建无需审批资源的预约得到 `CONFIRMED`；
- 创建需审批资源的预约得到 `PENDING_APPROVAL`；
- 审批驳回后时间片被释放；
- 用户取消后时间片被释放；
- 两个请求抢同一时段只有一个成功；
- 未签到任务重复执行不会重复扣分；
- 用户不能查看或取消他人的预约。

### 16.3 手工测试清单

- 参数缺失、超长、负数、非法日期；
- 资源停用和维护中；
- 闭馆日预约；
- 开放时间外预约；
- 跨日预约；
- 非 30 分钟边界预约；
- 容量超限；
- 用户被禁用；
- 待审批预约主动取消；
- 已取消预约再次取消；
- 已开始预约尝试取消；
- Token 过期；
- 普通用户手动调用管理员接口。

### 16.4 测试数据

演示环境至少准备：

- 1 个管理员；
- 3 个学生；
- 3 个资源分类；
- 6-10 个资源；
- 同时包含需要审批和无需审批的资源；
- 至少 30 条不同状态的预约；
- 至少 3 条违约记录；
- 明确的演示账号和密码。

不要让面试官打开系统后看到空页面。

## 十七、部署方案

### 17.1 本地开发

推荐本地开发时：

- IDEA 直接启动后端；
- `npm run dev` 启动前端；
- MySQL 和 Redis 可以本机安装，也可以 Docker 启动；
- 前端 Vite 代理 `/api` 到后端 8080，减少本地跨域问题。

### 17.2 第一次手动部署

在 9 月底前至少做一次手动部署：

1. Maven 打包后端 JAR；
2. 前端构建静态文件；
3. 上传到服务器；
4. 配置生产数据库和 Redis；
5. 使用命令启动 JAR；
6. 配置 Nginx；
7. 通过公网 IP 访问。

这一步是为了理解应用实际如何运行。完成一次后再切换 Docker。

### 17.3 Docker Compose 最终部署

最终 `deploy/` 目录建议包含：

```text
deploy/
├── docker-compose.yml
├── backend/
│   └── Dockerfile
├── nginx/
│   ├── nginx.conf
│   └── conf.d/booking.conf
└── .env.example
```

部署要求：

- MySQL 和 Redis 使用持久化 volume；
- 容器设置自动重启策略；
- 后端等待 MySQL 和 Redis 健康后启动；
- JVM 根据服务器内存设置合理上限；
- 日志目录挂载到宿主机；
- 数据库定期备份；
- 生产配置全部通过环境变量传入；
- Nginx 统一代理 `/api`，前后端使用同域名；
- 配置 HTTPS 时使用免费证书并设置续期。

### 17.4 上线检查

- [ ] 前端首页可访问；
- [ ] 登录和预约完整闭环正常；
- [ ] 浏览器刷新路由不会 404；
- [ ] Nginx 能正确代理 `/api`；
- [ ] MySQL 和 Redis 未暴露公网；
- [ ] 日志能找到一次完整请求；
- [ ] 容器重启后数据不丢失；
- [ ] 服务器重启后服务自动恢复；
- [ ] 演示账号可用；
- [ ] README 中没有真实密码和密钥；
- [ ] 数据库有最近一次备份。

## 十九、Git 与文档规范

### 19.1 提交原则

每完成一个可说明的小功能提交一次，不为了数量拆分无意义提交。

示例：

```text
feat: implement resource availability query
feat: add booking slot discretization
fix: release occupied slots after booking rejection
test: add concurrent booking JMeter scenario
docs: document database uniqueness strategy
```

提交前检查：

- 项目能编译；
- 没有提交密码和 `.env`；
- 没有调试用 `System.out.println`；
- 提交只包含当前功能相关改动；
- 提交信息说明目的。

### 19.2 必须维护的文档

```text
docs/
├── 01-requirements.md           # 需求与真实调研
├── 02-business-rules.md         # 业务规则和状态机
├── 03-architecture.md           # 系统架构和技术选型
├── 04-database-design.md        # ER 图、索引和关键取舍
├── 05-api.md                    # 接口入口或 OpenAPI 地址
├── 06-concurrency-test.md       # 并发问题复现与修复数据
├── 07-deployment.md             # 部署步骤
├── 08-troubleshooting.md        # 踩坑和排查过程
└── 09-demo-script.md            # 演示步骤和账号
```

### 19.3 技术决策记录

对关键选择写简短 ADR：

- 为什么使用 30 分钟时间片；
- 为什么唯一索引和 Redis 锁同时保留；
- 为什么使用单体而不是微服务；
- 为什么不使用物理外键；
- 为什么使用 SSE、MQ 等技术不适用于本项目；
- 为什么项目使用 Spring Boot 3.5 而不是 4.x。

每条只需说明：背景、候选方案、最终选择、代价。

## 二十一、落后时的砍需求顺序

如果进度落后，严格按以下顺序砍，不要随机删核心链路：

1. 砍复杂统计图表；
2. 砍站内通知；
3. 砍自动黑名单，只保留违约记录；
4. 砍资源图片上传；
5. 砍复杂资源分类，只保留一层分类；

7. 简化前端样式和页面合并；

- 登录和角色隔离；
- 资源与可用时段；
- 创建、取消、审批预约；
