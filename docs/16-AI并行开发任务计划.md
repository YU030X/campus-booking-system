# 校园预约系统 AI 并行开发任务计划

> 目的：把项目拆成可独立委派、可单独验收、合并冲突可控的任务包。
> 原则：不是所有任务从第一天同时开始；先冻结共享契约，再按依赖波次并行。
> 范围依据：`06-项目一详细方案.md`、`11-项目一数据库设计.md`、`15-项目一开发实施手册.md`。

## 一、总体组织方式

每个任务包必须对应：

1. 一个 OpenSpec change；
2. 一个独立分支 `codex/<change-name>`；
3. 一个独立 PR；
4. 一名实施 AI 和一名审阅 AI；
5. 明确的可编辑目录、只读契约、交付物和验证命令。

推荐为每个 AI 创建独立 Git worktree，避免共享工作区互相覆盖：

```bash
git worktree add ../campus-worktrees/<task-name> \
  -b codex/<change-name> main
```

每个任务遵循统一生命周期：

```text
OpenSpec propose
  → 人工/主控 AI 审阅
  → apply
  → 测试与构建
  → sync specs
  → validate specs
  → PR 审查
  → 合并
  → archive
```

## 二、依赖与并行波次

```text
波次 0  T00 治理初始化
          |
波次 1  T01 工程骨架与共享契约
          |
波次 2  T02 身份鉴权 ─┬─ T04 前端壳与认证
        T03 资源目录 ─┴─ T05 资源管理前端
          |
波次 3  T06 可用时段 ─── T07 预约核心与并发
                           ├─ T08 学生预约前端
                           └─ T09 审批与取消
                                  ├─ T10 签到、未到与违约
                                  └─ T11 管理端审批与用户
          |
波次 4  T12 缓存与支撑模块（P1，可延后）
          |
波次 5  T13 全量测试、压测与部署
```

同一波次只代表“可以并行”，不代表可以绕过前置验收门。

## 三、任务包清单

### T00：仓库治理初始化

- **Change**：`initialize-project-governance`
- **所有权**：`.gitignore`、`AGENTS.md`、`CONTRIBUTING.md`、`.github/`、`openspec/config.yaml`
- **目标**：完成模型调用、提交、PR、OpenSpec 同步和版本控制规范。
- **验收**：OpenSpec strict validate；治理文件可被 Git 跟踪；本地代理镜像与密钥仍被忽略。
- **完成门**：其余任务不得在治理规则未合并前创建 PR。

### T01：工程骨架与共享契约

- **Change**：`initialize-application-foundation`
- **所有权**：根构建入口、`booking-api/pom.xml`、`booking-web/package.json` 与锁文件、`sql/`、公共配置、统一响应/异常、OpenAPI 基线、前端 Axios/类型/路由壳。
- **交付物**：可启动的 Spring Boot 3.5.x/JDK 17 后端；可构建的 Vue 3/Vite 前端；12 表迁移脚本；统一错误码、分页、Long 字符串化、时间格式、角色和状态枚举契约。
- **验收**：`mvn verify`、`npm run build`、空库执行全部 SQL、OpenSpec strict validate。
- **禁止**：实现具体业务模块；其他 AI 不得并行修改上述共享文件。

### T02：注册、登录与用户权限

- **Change**：`add-identity-access`
- **所有权**：后端 `auth/**`、`user/**`、模块内测试。
- **交付物**：注册、BCrypt、登录、JWT、当前用户、STUDENT/ADMIN 权限、用户状态管理和数据归属校验。
- **验收**：正确/错误密码、Token 过期、401/403、学生访问管理员接口、密码非明文测试。
- **禁止**：访问预约 Mapper；擅自修改公共错误码、User 表或全局依赖。

### T03：资源、分类与开放规则

- **Change**：`add-resource-catalog`
- **所有权**：后端 `resource/**`、相关模块测试。
- **交付物**：分类、资源、开放时间、闭馆日 CRUD；资源状态、容量和可预约配置校验。
- **验收**：管理员写、学生读、闭馆与停用场景、一天多开放区间、全局闭馆规则测试。
- **禁止**：生成 `booking_slot`；实现预约状态机。

### T04：前端壳、注册与登录

- **Change**：`add-web-auth-shell`
- **所有权**：`booking-web/src/layouts/**`、`router/**`、`views/auth/**`、`stores/auth.*`、`api/auth.*`。
- **交付物**：登录注册页、布局、Token 注入、路由守卫、401/403 处理、角色菜单。
- **验收**：Mock 与真实 API 两种模式；刷新会话；登出；学生不能进入管理路由；前端 build。
- **禁止**：修改资源或预约页面；组件直接调用 Axios。

### T05：资源浏览与后台资源管理

- **Change**：`add-web-resource-management`
- **所有权**：前端 `views/resources/**`、`views/admin/resources/**`、`views/admin/categories/**`、`views/admin/rules/**`、`views/admin/closures/**` 及对应组件/API/store。
- **交付物**：学生资源列表/详情；管理员分类、资源、开放规则和闭馆日管理。
- **验收**：分页、筛选、加载/空/错误状态、权限、表单边界、资源启停刷新。
- **禁止**：实现预约提交；修改共享路由壳和 Axios 实例。

### T06：可用时段计算

- **Change**：`add-resource-availability`
- **所有权**：后端 `availability/**`、时间片纯函数及测试。
- **交付物**：查询资源未来指定日期的 30 分钟时间片；处理开放规则、闭馆、过去时间与已占用 slot。
- **验收**：00/30 对齐、左闭右开、同日限制、多开放区间、闭馆、过去 slot 过滤测试。
- **禁止**：创建预约；以缓存结果决定预约成功；修改 `booking_slot` 唯一索引。

### T07：预约核心与并发正确性

- **Change**：`add-concurrent-booking-core`
- **所有权**：后端 `booking/**`、`booking_slot` Mapper、预约事务服务、并发测试基线。
- **交付物**：创建/查询预约；时间片拆分；`booking` 与全部 slot 同事务；唯一索引冲突返回 409；资源+日期 Redisson 锁。
- **验收**：保留错误基线复现证据；50–100 请求抢同一时段只有一个成功；不同资源/日期不全局串行；事务回滚无残留。
- **禁止**：删除数据库唯一约束；将 Redis 作为正确性来源；使用带 `leaseTime` 的锁却宣称看门狗续期。

### T08：学生预约操作界面

- **Change**：`add-web-student-booking`
- **所有权**：前端 `views/booking/**`、`views/my-bookings/**`、`components/booking/**`、对应 API/store。
- **交付物**：可用 slot 选择、预约表单、我的预约、详情、状态时间线和取消入口。
- **验收**：只选 00/30；按钮 loading 防重；409 提示；取消后刷新列表与 slot；加载/空/错误状态。
- **禁止**：自造后端字段或状态；绕过共享 API 层。

### T09：审批与取消生命周期

- **Change**：`add-booking-approval-cancellation`
- **所有权**：后端 `approval/**`、取消服务、审批记录测试。
- **交付物**：待审批列表、通过、驳回、用户取消、迟取消违约入口；显式状态流转方法。
- **验收**：待审批创建时已占 slot；`REJECTED`/`CANCELLED` 同事务释放 slot；重复操作幂等；非法流转失败。
- **禁止**：提供任意目标状态的 `updateStatus(status)`；直接绕过预约领域服务更新状态。

### T10：签到、未到与违约

- **Change**：`add-checkin-no-show-violation`
- **所有权**：后端 `checkin/**`、`violation/**`、`task/**`。
- **交付物**：签到窗口、NO_SHOW 定时任务、违约记录、信用扣分、自动完成（P1 可选）。
- **验收**：签到所有权；时间窗口边界；重复任务不重复扣分；状态、违约、扣分、释放 slot 同事务；单条失败不回滚整批。
- **禁止**：只更新状态不释放 slot；把多条预约放进一个大事务。

### T11：后台审批与用户页面

- **Change**：`add-web-admin-operations`
- **所有权**：前端 `views/admin/approvals/**`、`views/admin/users/**` 及对应 API/store。
- **交付物**：待审批列表、通过/驳回、意见校验、用户状态管理。
- **验收**：管理员权限、二次确认、请求失败重新拉取、审批后状态刷新、非管理员 403 页面。
- **禁止**：修改资源后台目录；在前端自行推演非法状态流转。

### T12：缓存、通知、日志与统计（P1）

- **Change**：`add-supporting-capabilities`
- **所有权**：后端 `cache/**`、`notification/**`、`log/**`、`statistics/**`；对应 P1 前端目录。
- **交付物**：可用时段 Cache Aside、事务提交后失效；AOP 日志；站内通知；简单资源使用率统计。
- **验收**：Redis 失效不破坏数据库正确性；缓存前后对比；日志脱敏；通知幂等；统计 SQL 用 `EXPLAIN` 检查。
- **裁剪规则**：进度落后时依次砍统计、通知、缓存；不得影响 P0 上线。

### T13：系统测试、压测与部署

- **Change**：`verify-and-deploy-system`
- **所有权**：集成/E2E 测试、JMeter、`deploy/**`、部署与压测文档；原则上不修改业务实现。
- **交付物**：核心 API 集成测试、三轮并发报告、Docker Compose、Nginx、健康检查、备份与回滚 Runbook、演示数据。
- **验收**：后端 verify、前端 build、空库迁移、完整预约闭环、100 并发唯一成功、公网部署、重启数据不丢失、MySQL/Redis 不暴露公网。
- **禁止**：为通过测试而降低唯一约束、关闭鉴权或修改验收阈值。

## 四、共享文件单写者规则

以下文件不能由多个 AI 同时编辑：

| 共享区域 | 唯一所有者 |
| --- | --- |
| 根目录规范、`.gitignore`、PR 模板 | T00 |
| `pom.xml`、`package.json`、锁文件、全局配置 | T01 |
| OpenAPI、公共 DTO/类型、错误码 | T01；变更需契约评审 |
| SQL migration 编号与核心表结构 | T01；业务 AI 只提交变更请求 |
| 前端路由壳、Axios 实例、主题变量 | T04 |
| 预约状态机 | T07；T09/T10 通过公开方法扩展 |
| `deploy/**` | T13 |

任务需要修改共享文件时，不得直接改；应在 PR 中提交“共享文件变更申请”，由所有者以独立提交完成。

## 五、四个冻结契约

T01 合并前必须发布并冻结：

1. **数据库契约**：12 表字段、索引、迁移编号、`booking_slot` 物理删除规则；
2. **API 契约**：路径、方法、请求/响应、分页、错误码、401/403/409；
3. **领域契约**：预约状态、合法流转、30 分钟粒度、不可跨日、待审批占 slot、终态释放；
4. **前端契约**：路由、类型、API 模块、Mock/真实接口切换方式。

冻结后若需破坏性修改，必须新建 OpenSpec change；禁止在实现 PR 中静默改字段。

## 六、每个 AI 的任务卡模板

把以下内容原样复制给实施 AI，并填空：

```markdown
# 任务：<任务名>

- 仓库/worktree：<绝对路径>
- OpenSpec change：<change-name>
- 分支：codex/<change-name>
- 前置提交：<commit SHA>
- 可编辑路径：<精确目录/文件>
- 只读契约：<spec、OpenAPI、DDL 路径>
- 禁止事项：<不得修改的共享文件或业务边界>

## 目标
<可观察结果>

## 必须交付
- <代码/页面/迁移/测试/文档>

## 验收
- <具体行为>
- <真实命令及预期结果>

## 工作流
1. 用 OpenSpec propose 创建并完善 artifacts；等待审阅。
2. 获准后 apply；逐项更新 tasks。
3. 运行验证并保存真实结果。
4. 用 OpenSpec sync specs 合并 delta，验证 main specs。
5. 创建 Draft PR，附范围、非目标、证据、风险与回滚。

## 停止条件
契约不清、需要越出所有权目录、验证失败或发现设计冲突时停止并报告，不自行扩大范围。
```

## 七、统一 PR 门禁

每个 PR 必须满足：

- [ ] 一个 PR 只对应一个 OpenSpec change；
- [ ] 只修改任务卡允许的路径；
- [ ] change artifacts 与实现一致，tasks 已完成；
- [ ] 实际运行相关测试、构建和 `git diff --check`；
- [ ] 行为变化已通过 OpenSpec sync 合并到 main specs；
- [ ] main specs 验证通过；
- [ ] 无真实 `.env`、密钥、完整 JWT 或个人敏感数据；
- [ ] UI 改动附截图；
- [ ] 写明风险、回滚和未完成事项；
- [ ] 未完成任一项时保持 Draft，不得声称已经通过。

## 八、建议分配数量

不建议同时启用 14 个 AI。合理并发为 3–5 个：

- 波次 0/1：各 1 个 AI，串行完成；
- 波次 2：T02、T03、T04 最多 3 个并行，T05 在 T03 契约稳定后加入；
- 波次 3：后端按 T06 → T07 → T09/T10 的依赖推进，前端 T08/T11 可基于冻结 Mock 并行；
- 波次 4：仅在 P0 进度正常时分配 T12；
- 波次 5：T13 由独立测试/部署 AI 执行，主控 AI 只做最终裁决与验收。

任何时刻保留一名“集成主控 AI”不承担大块业务实现，专门负责契约、合并顺序、冲突裁决和最终验证。
