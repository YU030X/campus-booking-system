## 一、项目定位

这个项目的首要目标**不是做出一个多牛的系统，而是让你完整走通一遍"从需求到线上"的全流程**。第一次做会很慢很痛苦，这是必经过程。

三个必须达成的能力目标：

1. 独立完成从数据库设计到接口开发到前端联调到部署上线的全链路
2. 至少有一个能讲透的技术难点（并发预约控制）
3. 建立"我能做出东西"的信心

**不追求**：功能大而全、界面好看、高并发架构。

## 二、需求分析

### 问题描述

学校的琴房、实验室、研讨室、活动室、球场、投影仪等资源，目前普遍靠微信群接龙、纸质登记或者找管理员口头预约。存在的问题：时段冲突频繁、无法追溯谁用过、有人占了不来导致资源浪费、管理员无法统计使用情况。

> **建议**：真的去找一两个社团负责人或者实验室管理员聊十分钟，问他们现在怎么管的、最烦什么。这十分钟能让你的项目从"我编了一个场景"变成"我调研过真实需求"，面试时的说服力完全不同。

### 角色与核心流程

**普通用户（学生）**
浏览资源 → 查看可用时段 → 发起预约 → （等待审批）→ 到场签到 → 使用 → 结束

**管理员**
管理资源与时段配置 → 审批预约 → 处理异常 → 查看统计

### 关键业务规则

这些规则是项目复杂度的来源，也是面试时体现"你真的想过业务"的地方：

| 规则 | 说明 |
| --- | --- |
| 时段冲突 | 同一资源同一时段只能被一个预约占用 |
| 提前预约限制 | 最多提前 N 天预约（各资源可配置） |
| 单次时长限制 | 单次预约不超过 N 小时 |
| 并发持有限制 | 同一用户同时最多持有 M 个未完成预约 |
| 取消规则 | 开始前 X 小时可免责取消，之后取消记违约 |
| 签到规则 | 开始后 15 分钟内未签到，系统自动置为"未到"（`NO_SHOW`）、释放时段并记违约 |
| 信用机制 | 违约扣分，信用分低于阈值进黑名单，禁止预约 N 天 |
| 审批规则 | 部分资源需管理员审批，部分可直接预约 |

## 三、数据库设计

12 张表，规模适中。

### 核心表结构

**1. `user` 用户表**
```
id, username, password(BCrypt加密), real_name, student_no, phone,
role(STUDENT/ADMIN), credit_score(默认100), status, created_at, updated_at
```

**2. `resource_category` 资源分类表**
```
id, name, parent_id, sort_order, icon
```

**3. `resource` 资源表**
```
id, category_id, name, location, capacity, description, images,
need_approval(是否需审批), max_advance_days(最多提前几天),
max_duration_minutes(单次最长时长), status(可用/维护中/停用),
created_at, updated_at
```

**4. `resource_time_rule` 可用时段规则表**
```
id, resource_id, day_of_week(1-7), start_time, end_time
```
定义某资源每周几的几点到几点可预约。

**5. `resource_closure` 特殊闭馆表**
```
id, resource_id, closure_date, reason
```
处理节假日、临时维护等例外情况。

**6. `booking` 预约主表**
```
id, booking_no(业务单号), user_id, resource_id,
start_time, end_time, purpose, attendee_count, status,
checkin_time, cancel_time, cancel_reason, created_at, updated_at
```
`status` 状态机：`PENDING_APPROVAL`（待审批）→ `CONFIRMED`（已确认）→ `CHECKED_IN`（已签到）→ `COMPLETED`（已完成），以及 `REJECTED`（已驳回）、`CANCELLED`（已取消）、`NO_SHOW`（未到）。

> **只用一个 `status` 字段，不要再单独加 `approval_status`。** 审批的两种结果（待审批、已驳回）本身就是状态机里的两个状态，再开一个字段会产生两个字段互相矛盾的可能（比如 status=CONFIRMED 但 approval_status=REJECTED），这类"状态冗余"是维护噩梦。完整 DDL 见 `11-项目一数据库设计.md`。

**7. `booking_slot` 预约时段占用表（关键设计，见技术难点）**
```
id, resource_id, slot_time(时间片起点), booking_id
唯一索引：uk_resource_slot (resource_id, slot_time)
```

**8. `approval_record` 审批记录表**
```
id, booking_id, approver_id, action(APPROVE/REJECT), comment, created_at
```

**9. `violation_record` 违约记录表**
```
id, user_id, booking_id, violation_type(NO_SHOW/LATE_CANCEL),
score_change, remark, created_at
```

**10. `blacklist` 黑名单表**
```
id, user_id, reason, start_date, end_date, operator_id, created_at
```

**11. `notification` 通知表**
```
id, user_id, title, content, type, biz_id, is_read, created_at
```

**12. `operation_log` 操作日志表**
```
id, user_id, module, operation, params, ip, cost_ms, created_at
```
通过 AOP 自动记录，这个表本身就是 AOP 的一个好用例。

### 设计要点（面试会问）

- **为什么 `booking` 和 `booking_slot` 分两张表**：见技术难点部分，这是并发控制的核心设计。
- **索引设计**：`booking` 表需要 `(user_id, status)`、`(resource_id, start_time)` 等联合索引；要能解释为什么这么建、最左前缀原则怎么用上。
- **状态机字段**：为什么用状态枚举而不是多个布尔字段。
- **软删除还是硬删除**：预约记录用软删除保留审计痕迹。

## 四、技术难点详解

### 难点一：并发预约的冲突控制（本项目的灵魂）

这是整个项目最值得深挖的地方，也是你在面试里可以讲十分钟的内容。

#### 问题场景

两个同学同时点击预约同一个琴房的周六 14:00-16:00。如果处理不当，两个预约都会成功。

#### 错误做法（几乎所有初学者的第一版）

```java
// 有严重并发问题的写法
List<Booking> conflicts = bookingMapper.findConflicts(resourceId, start, end);
if (conflicts.isEmpty()) {
    bookingMapper.insert(newBooking);  // 两个线程可能同时走到这里
}
```

问题在于"检查"和"插入"之间存在时间窗口。两个请求可能同时通过检查，然后都插入成功。这就是典型的**检查后执行（Check-Then-Act）竞态条件**。

#### 为什么不能简单加唯一索引

直觉反应是"给 `(resource_id, start_time, end_time)` 加唯一索引"。但这解决不了问题，因为时间是**区间**：已有预约 14:00-16:00，新预约 15:00-17:00，两者 `start_time` 和 `end_time` 都不同，唯一索引拦不住，但它们实际重叠了。

**区间重叠不是相等，数据库的唯一约束天然只能约束相等。** 这个认知本身就是一个不错的面试回答。

#### 方案一：时段离散化 + 唯一索引（推荐的主方案）

核心思路：**把连续的时间区间切成固定粒度的离散时间片，把"区间重叠"问题转化为"离散值冲突"问题。**

以 30 分钟为一个时间片，预约 14:00-16:00 就是占用 `14:00`、`14:30`、`15:00`、`15:30` 四个时间片。往 `booking_slot` 表插入 4 条记录，该表在 `(resource_id, slot_time)` 上有唯一索引。

另一个请求要占用 15:00-17:00，需要插入 `15:00`、`15:30`、`16:00`、`16:30`，其中 `15:00` 和 `15:30` 已被占用，插入时数据库直接抛唯一键冲突异常，事务回滚，预约失败。

```java
@Transactional(rollbackFor = Exception.class)
public BookingVO createBooking(BookingDTO dto) {
    validateRules(dto);                       // 业务规则校验
    Booking booking = buildBooking(dto);
    bookingMapper.insert(booking);
    List<BookingSlot> slots = splitToSlots(booking);  // 拆成时间片
    try {
        bookingSlotMapper.insertBatch(slots);         // 唯一索引兜底
    } catch (DuplicateKeyException e) {
        throw new BizException("该时段已被预约，请刷新后重试");
    }
    return toVO(booking);
}
```

**这个方案的优点**：

- 正确性由数据库唯一约束保证，是最可靠的一层防线，不依赖应用层的任何假设
- 查询"某资源某天哪些时段可用"变成简单的等值查询，性能极好，而且能走索引
- 单机多机都适用，天然支持分布式部署

**要能讲清楚的取舍**：

- 粒度选 30 分钟是业务决定的（校园场景没有更细的需求）；粒度越细，占用记录越多，写放大越严重
- 一次预约要写多条记录，写入成本高于单条 insert，但换来了正确性
- 长时段预约（比如包场一整天）会产生较多记录，需要评估上限

#### 方案二：Redis 分布式锁（作为优化层）

在方案一之上加一层锁，把冲突拦截在数据库之前，减少无效的数据库操作和异常。

```java
String lockKey = "booking:lock:" + resourceId;
RLock lock = redissonClient.getLock(lockKey);
// 只传 waitTime，不传 leaseTime —— 这样看门狗才会生效
boolean locked = lock.tryLock(3, TimeUnit.SECONDS);
if (!locked) {
    throw new BizException("当前预约人数较多，请稍后重试");
}
try {
    // 检查 + 创建
} finally {
    // 必须判断持有者，否则锁已过期时 unlock 会抛 IllegalMonitorStateException
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

**要能讲清楚的点**：

- 锁的粒度：按 `resourceId` 加锁，而不是全局锁，不同资源之间互不阻塞

- **为什么这里不传 `leaseTime`（这是个高频陷阱）**：Redisson 的看门狗（watchdog）只在**没有显式指定 leaseTime** 时才启动。一旦你写成 `tryLock(3, 10, TimeUnit.SECONDS)`，就等于告诉 Redisson"我自己管过期时间"，看门狗直接关闭——业务如果跑超过 10 秒，锁会提前释放，另一个线程就能同时进入临界区。
  很多人一边写着带 leaseTime 的代码，一边在面试里讲"我用了看门狗自动续期"，这是自相矛盾的，稍懂的面试官一问就穿。**正确的做法是只传 waitTime，让看门狗按默认 30 秒租约每 10 秒续一次。**

- **`unlock()` 前要判断 `isHeldByCurrentThread()`**：如果锁因为异常情况已经过期释放，直接 unlock 会抛 `IllegalMonitorStateException`，把真正的业务异常掩盖掉。

- 为什么还要保留数据库唯一索引：Redis 锁在极端情况下会失效（主从切换丢锁、Redis 宕机），**分布式锁是性能优化，数据库约束才是正确性保证**。这句话本身就是很成熟的工程认知。

- 为什么不用 `setnx` 手写锁（解锁的原子性需要 Lua 脚本、不可重入、无法续期）

#### 方案三：悲观锁 / 乐观锁（作为对比讲）

`SELECT ... FOR UPDATE` 锁住资源行，简单但并发性能差。乐观锁用 version 字段，适合冲突少的场景。

面试时能把这三类方案的适用场景、优缺点对比着讲，是很强的加分项。

#### 建议的实现顺序

先写出有并发问题的第一版，然后**用 JMeter 或写个多线程脚本压测，亲眼看到重复预约产生**，再逐步加上唯一索引、加上分布式锁。

这个过程本身就是最好的简历素材——"我发现了什么问题、怎么复现的、怎么解决的、验证效果如何"，这个叙事结构比任何技术名词堆砌都有说服力。

### 难点二：缓存设计与一致性

**场景**：查询"某资源未来 7 天的可用时段"是最高频的操作，每次都查数据库并计算可用性，压力大。

**做法**：把计算结果缓存到 Redis，key 设计为 `resource:slots:{resourceId}:{date}`。

**要处理的问题**：

- **缓存失效时机**：预约成功、取消、审批通过、管理员改配置时，都要删除对应缓存
- **缓存穿透**：查询不存在的资源 ID，每次都打到数据库。用空值缓存或布隆过滤器
- **缓存击穿**：热门资源缓存过期瞬间大量请求涌入。用互斥锁重建缓存
- **一致性策略**：为什么选"先更新数据库，再删除缓存"（Cache Aside）而不是"更新缓存"

---

### 难点三：定时任务与幂等性

**场景**：每分钟扫描一次，把"开始超过 15 分钟仍未签到"的预约自动置为 `NO_SHOW` 并记违约。

**要处理的问题**：

- **幂等性**：任务重复执行会不会重复扣分？用状态判断 + 数据库唯一约束保证只执行一次
- **执行效率**：全表扫描不可取，要设计合适的索引和查询条件
- **单机 vs 分布式**：如果部署两个实例，定时任务会执行两次。理解这个问题（解决方案是分布式锁或分布式调度框架 XXL-Job），即使项目里只部署单机，也要能说出来

---

### 难点四：统一工程规范

这部分不算"难点"但决定代码质量，面试官看代码时会注意：

- 统一响应结构 `Result<T>`
- 全局异常处理 `@RestControllerAdvice`
- 业务异常体系与错误码设计
- 参数校验 `@Valid` + 自定义校验注解
- AOP 记录操作日志和接口耗时
- DTO / VO / Entity 分层，不要把数据库实体直接返回给前端

## 七、面试讲解框架

**开场 30 秒**：

**主动引导到难点**：
"这个项目里我花时间最多的是并发预约的冲突控制。最开始我的实现有个典型的竞态条件问题……"

然后自然展开：问题现象 → 怎么复现 → 分析原因 → 方案对比 → 最终选择 → 验证效果。

**准备好被追问的问题**：

1. 为什么不用唯一索引直接约束时间区间？
2. 时间片粒度为什么选 30 分钟？改成 5 分钟会有什么问题？
3. Redis 锁和数据库唯一索引，为什么两个都要？
4. Redisson 的锁续期是怎么实现的？
5. 如果 Redis 挂了，你的系统还能正常工作吗？
6. 缓存和数据库不一致怎么办？为什么选择删除缓存而不是更新缓存？
7. 定时任务如果部署了两个实例会怎样？
8. 这个系统能承受多大并发？你怎么测的？瓶颈在哪？
9. 状态机的状态流转你是怎么控制的？如果有非法流转怎么办？
10. 如果现在要支持一万人同时抢一个热门场地，你会怎么改？
